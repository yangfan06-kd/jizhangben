# 面试知识整理

这里把项目经验转换成面试时可以清楚说明的技术问题和回答思路。

## 当前可以讲的内容

### 为什么不直接重写项目？

因为现有项目已经有真实业务、数据格式和用户操作流程。渐进式重构可以保留可用功能，在每一步验证结果，降低数据丢失和功能回归风险。

### 为什么先做前端工程化？

当前所有代码集中在一个入口文件中。先拆分职责，可以降低模块之间的耦合，让后续接入后端、测试和多人协作更容易。

### localStorage 有什么限制？

它适合单浏览器和单用户场景，但不能提供真正的跨设备同步、用户隔离、权限控制和可靠的服务端备份，因此在线版本需要迁移到后端数据库。

### 如何避免编辑表单保存成新增？

我把账户和账本的编辑 ID 放到统一的 `uiState` 中。进入编辑时保存对象 ID，保存时根据 ID 选择更新或新增分支，保存成功和取消操作都通过 reset 函数清空 ID。这样即使页面重绘，编辑上下文仍然明确，并用新增、修改、取消和删除流程验证没有重复数据。

### 如何划分前端状态？

我按生命周期把状态分成两层：账本、账目、账户和自定义选项属于需要持久化的 `dataState`；当前标签页、表单选择和图表选择属于会话级的 `uiState`。视图只读取状态并渲染，状态变化后调用统一刷新入口，避免按钮、筛选和统计图出现不同步。

### 如何拆分一个传统多脚本页面？

我先提取跨模块复用的纯函数，放到 `helpers.js`，再按“常量、状态、工具、存储、业务模块、启动”的顺序加载。这样模块可以共享金额和日期规则，但不会在加载阶段互相执行；每次拆分后都用真实浏览器流程验证页面仍能新增、显示和删除数据。

### 如何设计押金这类特殊业务的前端交互？

我把押金方向、原押金关联和最终结算提示放在独立的 `deposit-form.js`，把收入/支出计算继续交给领域计算模块。支付 1000 元时只记录资金流，退回 700 元并勾选最终结算时才把 300 元差额计入支出；通过真实浏览器场景验证了字段显隐、账户校验和最终统计。

### 如何把数据状态转换成下拉控件？

我把账户和类别下拉的 DOM 生成放在 `selects.js`。账户新增、编辑或删除后，由 `renderAccountSelects()` 统一刷新记账页和明细页的账户选项；类别变化后调用 `fillCategoryFilter()` 刷新类别筛选。这样列表、表单和筛选不会各自维护一份选项，也方便以后把 localStorage 数据替换成接口返回的数据。

### 为什么要增加存储适配层？

我把直接访问 `localStorage` 的代码集中到 `storage-adapter.js`，提供单键读写和备份所需的批量操作。`storage.js` 负责账本数据的解析和保存，`backup.js` 负责备份格式与回滚，业务模块不再关心浏览器存储细节。这样将来切换 IndexedDB 或后端 API 时，可以先替换适配层，同时保留现有数据键名和用户功能。

### 如何保证旧版本数据可以升级？

我在 `migrations.js` 中保存 schema 版本，并按版本逐步执行迁移。v1 会把旧版单账本的记录和账户键移动到默认账本的分账本键，v2 会把旧金额字段规范化为 `amountCents`、`initialCents` 并写回。每一步都设计成可重复执行，只有完成后才写入新版本号；页面中断后再次打开不会因为重复执行而覆盖已有数据，也能继续增加 v3。

### 如何避免数据迁移停在一半？

迁移开始前，我先保存所有记账本键的内存快照。任何写入异常都会传播到统一的迁移入口，由它删除本次新增键、恢复原值并保留旧 schema；页面同时提示用户数据已恢复。测试时我故意让账户写入失败，验证记录改写被撤销、版本没有前进，随后恢复写入并确认刷新后可以重新升级。

### 如何给传统前端脚本补自动化测试？

这个项目最初使用多个普通 `<script>`，函数依赖加载顺序，也没有模块导出。我用 Node 内置的测试运行器和 `vm`，按页面顺序执行真实脚本，并实现内存版 `localStorage` 隔离测试数据。首批 6 个用例覆盖小数金额转分、旧记录和账户规范化、schema v1/v2 连续迁移、中途写入失败回滚，以及损坏 JSON 保留。这样不引入第三方依赖，也不会为了测试复制一套业务代码。

### 如何验证押金和负债账户这类复杂计算？

我先把业务规则写成具体场景：付出 1000 元押金并全额退回时收支为 0；分次一共退回 700 元并最终结算时，只有 300 元进入支出；主动收取押金后少退的部分则进入收入。账户测试同时覆盖资金账户、负债账户和从资金账户向负债账户还款的转账，并用“资金余额减负债余额等于净资产”校验整体结果。测试还发现计算中途仍在累加元的小数，我把余额和押金差额统一改为整数分计算，使 0.10 加 0.20 可以严格得到 0.30。

### 为什么备份能解析为 JSON 还不够？

JSON 解析只能证明文本语法正确，不能证明它包含可用的账本数据。我在导入前继续检查备份版本、允许的存储键、数组结构，以及账本、账目、账户和自定义选项的关键字段；高于当前程序的版本和未知键会被拒绝。为了兼容老用户，旧版扁平备份仍有单独测试。真正写入时先保存当前数据快照，模拟中途失败后验证所有原值都能恢复。

### 如何验收一个响应式手机页面？

我在真实 Edge 浏览器中使用 320px、375px 和 768px 三种视口，逐一检查记账、账户、明细、总览和账本管理页。除了确认文档宽度不超过视口，我还读取每个可见按钮、输入框和下拉框的边界，要求主要触控区域至少 44px。初次检查发现页面没有横向滚动，但编辑、删除和备份按钮仍然偏小；调整分层媒体查询后，15 个场景的溢出数和小控件数都降为 0，并在 320px 下完成了一次新增、查看和删除账目的完整流程。

### 如何把 localStorage 项目迁移到关系数据库？

我先识别现有数据之间的真实关系，而不是把每个 localStorage 数组原样塞进一列 JSON。用户拥有账本，账本拥有账户和账目，账目关联类别、类型、转出账户、转入账户，并通过自关联连接原押金。金额在接口和数据库中只保存整数分。迁移时先导入父级数据并建立旧 ID 到 UUID 的映射，账目分两遍导入，第二遍补齐转账和押金关联；整个过程放在事务中，并用数量、收支和净资产对账后再提交。

### 如何验证 FastAPI 服务和数据库真的可用？

我提供 `create_app()` 应用工厂，让测试把数据库路径替换成临时 SQLite。测试用 `httpx2.AsyncClient` 通过 ASGI transport 调用真实 `/api/health`，同时显式运行 FastAPI lifespan；断言不仅检查 HTTP 200 和响应 JSON，还直接检查数据库文件及 `schema_migrations` 表。最后再启动 Uvicorn 发起真实 HTTP 请求，区分“函数测试通过”和“服务能够运行”这两个层次。

### 如何管理关系数据库的结构升级？

我用 `schema_migrations` 保存已执行版本，应用启动时只运行缺失的迁移，并把建表、索引和版本记录放在同一个 SQLite 事务中。第一版建立用户与账本关系：邮箱忽略大小写后仍唯一，账本必须属于真实用户，删除用户会级联删除账本。我没有只验证表名，而是用重复初始化和三种约束场景证明迁移幂等、外键开启且删除规则有效。

### 如何保证数据库里的金额始终是整数分？

前端计算已经统一使用整数分，后端账户本金也使用 `initial_cents`。考虑到 SQLite 的 `INTEGER` 是类型亲和性而不是绝对的强类型限制，我额外检查实际存储类型必须是 `integer`，并要求数值大于等于 0。测试明确尝试写入负数和 `1.5`，两者都会失败，避免浮点金额绕过接口后污染余额计算。

### 如何保留已经停用的类别和记账类型？

类别和类型被历史账目引用后不再物理删除，而是写入 `archived_at`。我用部分唯一索引只约束未归档记录，因此有效选项不能重名，归档后又可以重新使用原名称。记账类型进一步分为稳定 `code`、显示 `name` 和计算用 `behavior`，即使界面名称改变，历史收支逻辑也不会跟着变化。

### 账目规则应该放在数据库还是服务层？

金额必须是正整数分、日期必须有效、外键必须存在、转出转入不能相同，这些单行规则由数据库约束。账户是否属于当前账本、类型行为是否需要账户、退回押金是否关联方向匹配的原押金，需要读取其他数据，由服务层在事务内校验。这样数据库守住基础完整性，复杂业务规则仍保持可读、可测试，并能返回用户理解的错误信息。

### 如何防止不同用户的账目数据串在一起？

创建账目时，我先通过账本确定所有者，再用该 `user_id` 查询有效类别和记账类型，账户则必须同时匹配当前 `book_id`。校验与插入共用一个 SQLite 事务，任何失败都会返回稳定业务代码且不写入数据。测试会传入另一个用户真实存在的 ID，证明外键通过的情况下服务层仍能阻止跨用户写入。

### 如何设计前后端都容易处理的 API 错误？

我按失败性质使用 404、409 和 422，同时让错误体始终从根级返回稳定 `code` 与用户可读 `message`。Pydantic 字段错误另外携带 `details`。手机端按错误代码决定提示或操作，中文文案可以调整而不破坏程序；测试同时断言状态码和响应结构，防止接口后续出现格式漂移。

### 没有正式登录时，如何为后端建立可替换的用户边界？

阶段 3 的应用启动流程会幂等建立一个固定本地开发用户，请求通过统一依赖取得当前用户 ID，路由再把它显式交给服务层。这个开发身份只用于本地联调；阶段 4 接入登录会话时可以替换依赖的实现，而账本和账目服务仍按同一参数工作。测试重复运行启动流程，确认用户不会重复创建，并用另一个用户的真实账本验证越权请求返回 404 且不写入。

### 同名账本为什么返回警告而不是报错？

项目原有规则允许同一用户建立同名账本，所以后端不能擅自增加唯一限制。创建服务先检查忽略大小写的同名记录，仍完成创建，再在响应的 `warnings` 中返回稳定的 `duplicate_book_name`。这样客户端可以醒目提醒用户，同时保留用户继续保存的选择，行为与现有前端一致。

### 如何保证账户 API 不会跨账本或跨用户写入？

我把账户接口设计成嵌套在账本路径下，但不会把路径中的账本 ID 当作授权证明。服务层首先按当前用户和账本 ID 一起查询父账本，只有匹配后才读取或插入账户。资金和负债使用固定 `kind` 值，初始金额只收非负整数分；字段问题返回统一 422，账本不存在或不属于当前用户统一返回 404。测试会建立另一个真实用户的账本，确认查询和创建都被拒绝且没有落库。

### 如何查询类别和记账类型，同时不让历史归档项重新出现？

类别和类型属于用户级资源，因此接口只按当前用户查询，不依赖某个账本 ID；查询条件固定包含 `archived_at IS NULL`，让归档项继续服务历史账目，却不会出现在新账目选择框。类型响应同时保留显示名称、稳定 `code` 和 `behavior`，客户端用行为字段决定收入、支出、转账或押金规则。测试会插入当前用户、归档记录和其他用户记录，证明接口只返回当前用户的有效选项。

### 为什么不能总用创建时间和 UUID 排序？

SQLite 默认创建时间是秒级的，连续插入的数据可能拥有完全相同的时间；如果再比较随机 UUID，列表顺序就会随机变化。账户列表需要展示创建顺序，所以我使用实际插入顺序；类别和类型需要稳定易读的选择顺序，所以使用系统标记、名称和 ID。排序规则应表达产品需求，并通过测试固定下来。

### 如何安全地开放自定义类别和记账类型创建？

类别创建只接受名称，类型创建只接受格式受限的小写代码、名称和收入/支出/中性行为。服务端而非客户端决定 `is_system=false`，所以用户不能伪造内置项；转账、押金等特殊行为仍由系统类型提供。创建前服务层会按当前用户检查有效名称和稳定代码冲突，并以 409 返回明确错误代码；数据库唯一索引继续作为最终保护。这样前端能给出准确提示，业务规则也不会被自由输入破坏。

### 如何设计既安全又方便渲染的账目查询接口？

我先按当前用户和账本 ID 确认访问边界，再用参数化 SQL 组合日期、账户、类别和关键词条件。查询结果不会只给外键 ID，而是通过关联类型、类别和账户表，一次返回类型名称、稳定代码、业务行为和账户名称；账户使用左连接，历史账目即使账户已删除也能正常显示。这样手机端加载一页明细只需一次请求，不会对每条记录产生额外请求。

### 如何安全删除带业务关联的账目？

删除前我依次验证当前用户拥有账本、账目属于该账本、是否存在押金退回记录引用它。普通账目删除后返回 204；已被结算记录引用的原押金返回 `deposit_record_in_use`，用户需要先处理关联退回记录。这样不会把数据库外键错误直接暴露给客户端，也能保留完整的押金对账链路。

### 如何保证账目修改不会绕过创建规则？

完整修改使用与创建相同的请求结构，并把路径中的记录 ID 固定后重新构造领域对象，调用同一套账户、类别、类型和押金校验。无效修改会在事务中失败，原账目保持不变。对于已完成押金结算的两端记录，我选择锁定直接修改，避免编辑一端后让已有退回方向或金额关系失效；需要调整时先按明确顺序处理关联记录。

### 删除账户后怎样保留历史账目？

账户是可管理资源，账目是历史业务事实，不能因为用户删除一个账户就一并删除账目。数据库将账目中的账户外键设为 `ON DELETE SET NULL`：账户删除后，账目继续保留，界面显示为未指定账户。测试会建立带账户引用的历史账目，再执行删除并直接检查引用已变空、账目仍存在。

### 为什么类别和记账类型使用归档而不是物理删除？

类别和记账类型是账目的历史维度。用户点击删除时，接口只写入 `archived_at`，所以它们从新建表单消失，但旧账目仍能通过外键找到名称和业务行为。自定义类别可以改名；记账类型只改显示名称，稳定 `code` 与 `behavior` 不可改，防止历史统计口径漂移。系统项和其他用户资源会被保护，测试覆盖 200、204、409 和 404。

### 后端总览如何同时计算余额和期间收支？

我先用全部历史账目从账户本金开始重放余额：资产账户流入加、流出减，负债账户符号反转；转账同时更新两个账户但不计收入支出。然后用 `from`、`to` 过滤期间事件，按类型行为累计收入和支出，押金只在最终结算时计算原金额与所有退回金额的差额。所有金额都使用整数分，最后按账本和全部账本汇总，测试覆盖跨月、负债和押金场景。

### 如何设计服务端备份导入，避免数据串账？

备份只导出当前用户的数据，不携带密码或其他用户信息，并带有明确格式和版本号。导入时先校验账本、账户、类别、记账类型和账目的所有 ID 及跨表关系，再在一个事务中清理当前用户旧数据，为每个来源 ID 生成新 UUID，按父表到子表的顺序重建关系；押金记录按 `deposit_link_id` 依赖顺序插入。返回结构化 `id_map`，方便迁移后的客户端更新引用，任何校验失败都不会删除原数据。

### 如何安全修改和删除账本？

账本修改和删除都先按当前用户与账本 ID 一起确认所有权，因此知道其他用户的资源 ID 也不会越权。改名沿用已有产品规则：允许同名，但返回稳定的 `duplicate_book_name` 提示。删除账本时，我把它视为账户和账目的聚合根，使用数据库级联删除清理其下属数据；类别和类型仍属于用户，不会被误删。测试同时覆盖同名修改、HTTP 204 和删除后的三张表状态。

### 为什么网页接入后端要先做“后端读、本地写”？

我没有一次性替换所有读写路径，而是先增加独立的数据访问层：页面启动先用 localStorage 渲染，再异步尝试读取服务端账本和账户；服务端返回空数据、请求失败或页面是 `file://` 时继续使用本地数据。服务端 UUID 作为不透明字符串保留，避免被旧代码强制转成数字。成功读取后页面明确提示当前阶段新增、修改和账目明细仍在本地，这样可以逐步验证接口和映射，等迁移对账完成后再切换写入。

### 多个接口如何保证页面不会混用两套数据？

账本、选项、账户、明细和总览共同构成一次页面快照。我在启动前保存 localStorage 的整组状态，后端响应全部通过结构校验和字段映射后才统一替换；任何一个接口失败就恢复整组本地状态。服务端系统类别和类型不再重复加入前端自定义数组，总览也使用服务端摘要，避免统计卡片和总览分别来自不同来源。

### 如何在不碰真实数据的情况下演练 localStorage 迁移？

我先构造一份只含虚构名称和金额的 localStorage 备份，用离线转换器生成服务端备份格式。转换时给账户和账目 ID 加上账本作用域，再调用临时 SQLite 上的事务式导入接口；导入后逐项比较账本数、账户数、账目数、收入、支出、押金差额和净资产，并检查服务端返回的 `id_map` 是否重建了转账和押金关联。最后把一个账户引用改成不存在的账本，确认接口返回 422 且旧服务端数据保留。整个过程不读取真实浏览器存储，也不使用正式数据库。

### 如何在用户确认前预览迁移结果？

网页把备份发给只读的 `/api/backups/preview-local`，服务端先转换旧 localStorage 结构，再校验所有跨表关系，并返回账本、账户、账目数量以及分账本和总计的收入、支出、净资产。预览只在内存中计算，不执行删除、UUID 重建或数据库写入；用户确认后才把同一份服务端 payload 交给事务式导入接口。测试会在预览后再次查询服务端账本为空，并用押金少退差额验证预览和正式总览使用同一口径。

### 网页迁移确认时如何防止误导入和重复提交？

我保留原有的本地备份导入按钮，单独增加“预览迁移”流程。用户选择文件后，页面先校验备份结构，再请求 `/api/backups/preview-local`，只有收到数量和金额摘要后才启用确认按钮；确认时按钮立即禁用，只调用一次 `/api/backups/import-local`。取消、预览失败、网络失败或导入失败都保留浏览器原始数据，导入成功后重新读取整组服务端快照。

### 如何渐进式切换前端写入而不混用两套主键？

我先只切换新建账本和新建账户：请求成功后采用服务端返回的 UUID，并刷新服务端总览；修改、删除和账目写入暂时保留原来的 localStorage 流程。若请求失败，先从 localStorage 重新加载完整快照，再执行本地保存，避免把后端 UUID 直接写进旧数字 ID 的数据集。测试同时覆盖成功响应、URL 编码和网络失败回退。

### 如何把网页新建账目转换成后端请求？

网页表单使用中文名称和本地下拉值，后端请求使用类型 UUID、类别 UUID、账本内账户 UUID 和整数分金额。我在读取服务端选项时保留名称到 UUID 的映射，新建时按类型决定是否提交账户和转入账户；押金额外转换方向、对象、原押金 ID 和最终结算标记。服务端成功响应只有外键 ID，所以客户端用本次表单名称补全显示模型，并采用服务端返回的记录 UUID。

### 账目写入失败时如何保证本地回退仍然可用？

失败不能直接把 UUID 快照写回旧 localStorage。我先重新加载本地账本、账户和记录，再用账户名称把服务端 UUID 转回本地账户 ID；如果是押金退回，则用原押金的类型、类别、日期、金额和对象等业务指纹重新找到本地记录。这样普通账目、转账和押金回退都落在同一套本地数据模型里，原有余额和差额计算继续有效。

### 异步保存如何避免重复账目？

保存按钮触发后，我在页面状态中记录请求进行中，并禁用保存和取消按钮；后续点击只显示等待提示，不再发起请求。服务端创建成功后，客户端先保留返回记录，再单独请求当前账本明细。明细请求失败不会把已经成功的创建当成失败回退，从而避免服务端记录和本地副本同时出现。

### 为什么服务端冲突不能自动回退到本地？

网络断开时本地回退可以保证用户继续记账；服务端返回业务错误码时则说明请求已经到达，但违反了押金关联、账户归属或字段规则。此时如果自动保存本地，就会让两边结果不同。因此我保留表单内容和服务端说明，让用户修正后重新提交；只有没有业务错误码的网络类失败才进入本地回退。

### 账目修改和删除如何与后端保持一致？

编辑账目时，我把表单重新转换成与创建相同的请求结构，调用 `PUT /api/books/{book_id}/records/{record_id}`，成功后采用服务端响应并重新读取明细和总览。删除调用对应的 `DELETE` 接口，并正确处理 HTTP 204 空响应。服务端返回 `deposit_record_in_use` 或 `deposit_settlement_locked` 时保留业务冲突，不能通过本地删除或修改绕过押金对账规则。

### 修改或删除请求失败时，为什么要使用业务指纹？

服务端记录使用 UUID，而旧浏览器数据可能使用数字 ID，直接复制服务端主键会破坏本地引用。回退前我先恢复 localStorage 快照，再用原记录的类型、类别、日期、金额、备注、账户名称和押金对象定位本地目标；找到后才执行本地修改或删除，找不到就停止并提示用户。这种做法把跨存储回退建立在稳定业务字段上，而不是建立在不兼容的主键上。

### 账本和账户的修改、删除如何接入而不影响派生数据？

账本修改和删除分别调用 `PATCH`、`DELETE`；账户修改和删除调用账本作用域下的 `PATCH`、`DELETE`。服务端写入成功后，账本刷新总览，账户删除还重新读取当前账本明细，因为历史账目会保留但账户引用会变成未指定。刷新失败只提示重试，不能把已经成功的删除重新写成本地结果。

### 三类资源如何共用网络失败回退规则？

我把服务端业务错误和网络错误分开：业务错误说明请求已到达但违反领域规则，页面保留对象和错误说明；只有网络类错误才恢复 localStorage。账目用类型、类别、日期、金额和账户等字段定位，账本用名称和分类定位，账户用名称、类型和本金定位；如果匹配不唯一就停止回退，避免误改同名对象。

### 密码和会话如何设计？

用户密码使用 PBKDF2-HMAC-SHA256 加随机盐保存为结构化哈希字符串，数据库不保存明文。登录成功后生成高熵随机令牌，浏览器通过 HttpOnly、SameSite Cookie 保存，数据库只保存令牌的 SHA-256 摘要和过期时间；每个业务请求在统一依赖中解析会话，再用会话用户 ID 做账本边界校验。

### 如何在不一次性破坏旧页面的情况下接入认证？

我先新增 schema v5 和独立认证接口，并让请求依赖优先使用有效会话；没有 Cookie 时暂时使用明确的开发回退开关，带无效 Cookie 则直接 401。这样可以先验证注册、登录、退出和用户隔离，再接入网页登录界面，最后关闭回退开关，避免把认证迁移和前端重构绑成一个不可回退的大改动。

### 会话过期时前端如何保持一致？

请求层保留 HTTP 状态码，只对受保护业务接口的 401 发出会话失效通知，认证接口自己的 401 仍由登录表单显示密码或邮箱错误。认证模块收到通知后清空用户和登录状态，恢复启动时保存的 localStorage 快照并提示重新登录；后端同时在查询会话时删除过期令牌。这样页面不会继续显示“已登录”却把每次写入都当成失败，也不会把密码错误误判成会话过期。

### 登录成功但服务端数据暂时读不到怎么办？

我把认证结果和数据读取结果拆开。登录接口成功后先保留当前用户；如果账本、选项或明细读取失败，页面回到本地快照但仍显示已登录，并在顶部通知用户稍后重试。只有业务接口明确返回 401 才清除会话。主动退出时则撤销 Cookie、清空认证状态并明确标注当前使用本地数据，避免用户误以为页面仍在同步服务端。

### 如何证明备份迁移属于正确的登录用户？

我在临时数据库中先注册一个独立用户，复用同一个带 Cookie 的客户端完成迁移预览、导入、导出和总览读取，再比较账本、账户、账目数量以及收入、支出、净资产。导出回读还会检查押金退回记录已经指向新的原押金 UUID；退出后再次查询只显示开发用户数据，证明迁移没有落到错误的用户边界。

### 如何验证手机和电脑登录后看到的是同一份数据？

我创建两个独立的 HTTP 客户端，分别保存各自的 Cookie。第一个客户端注册并创建账本、账户和账目，第二个客户端用同一账号登录后读取这些资源和总览，比较关键 ID、金额和记录内容；再用第三个账号访问同一账本，确认返回 404。这样同时验证了会话共享、服务端持久化和跨用户隔离，而不是只证明单个请求成功。

### 你的持续集成检查什么？

GitHub Actions 在 Ubuntu 干净环境中固定 Node.js 22 和 Python 3.12，运行与本地相同的前端 71 项测试、逐文件 JavaScript 语法检查，以及从 `requirements.txt` 安装依赖后的后端 102 项回归。工作流同时监听 `main` 推送和合并请求，能发现依赖、运行环境和代码回归问题。之前 CI 失败是因为项目使用了 Node.js 23/24 风格的 `--test-isolation=none`，而 Node.js 22 需要实验性参数名；我根据具体失败步骤改正测试脚本，并保留 Node.js 22 的 CI 运行时。

### 如何避免把开发 API 地址带进正式 App？

调试包通过 USB 转发使用 `http://localhost:8000/api`，这只代表手机上的开发入口。为避免发布包安装后把请求发回手机自身，我增加了独立的正式地址预检：要求完整 HTTPS URL、`/api` 路径，拒绝 localhost、回环地址、示例域名和嵌入式账号密码。预检作为构建前的显式命令运行，真实域名准备好后才进入签名包流程。

我又把预检接入 `app:build:release`，脚本只有在地址通过后才同步网页资源和执行 Gradle；当前没有签名密钥时明确输出未签名 APK，避免把“能构建”误认为“能发布”。同时，服务端成功快照会写回设备 localStorage，使移动端保留最近一次可用数据。

针对移动网络不稳定的情况，我让 App 在启动认证遇到真正的网络错误时加载最近一次本地快照，显示离线状态；HTTP 401 等明确认证错误仍保持登录门。用户点击“联网登录”后再恢复远程会话，避免把断网和账号错误混在一起。

我还监听 WebView 的 online/offline 事件：离线时提示新增账目会先落本机，恢复网络时提示点击“联网登录”或“同步”，让用户知道何时可以把本地状态重新接回服务端。为避免离线写入被旧服务端快照覆盖，我给本地写入增加待同步标记；如果服务端已有账本，登录和手动同步会暂缓替换并引导先导出、预览和迁移，完整服务端快照成功读取后才清除标记。

### 你如何验证部署后的跨设备会话？

我先用 Uvicorn 在真实 HTTP 端口启动同源服务，再创建两个独立的 Cookie 会话。第一个会话注册用户并创建账本、账户，第二个会话登录同一账号后读取这些数据和服务端备份；最后用第三个账号确认账本列表为空，访问第一个账号的账户返回 404。这样验证了静态网页、Cookie 登录、服务端持久化和用户隔离，而不是只依赖 ASGI 模拟请求。
