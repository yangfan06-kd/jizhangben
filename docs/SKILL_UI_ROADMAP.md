# 结合设计技能的下一阶段路线（2026-10-15）

## 本轮结论

下一阶段以现有离线版为基础，先审查并统一设计规则，再依次完善首页、记一笔、类别管理及其他页面。已确认的页面结构、紧凑密度和记账习惯继续作为依据。每次只改一组可验收的问题；技能用于帮助判断和验证，不是更换框架或重做业务的理由。

本文件承接 [原界面路线](UI_EVOLUTION_PLAN.md) 和 [性能实验](PERFORMANCE_EXPERIMENT.md)。旧路线中的早期问题、阶段顺序属于历史快照；此后的实施顺序以本文件为准，已完成事项不重复立项。后续用户的新指令优先。

路线初次制定时仅交付计划；后续实施记录见下节。每阶段均单独说明是否修改生产界面，不将原型、构建和装机混为一谈。

## 固定的设计与数据约束

- 保留 HTML/CSS/JavaScript + Capacitor，优先沿用现有控件和本地 SVG。此路线不引入 React、Flutter、整套 UI 框架、在线字体或远程图片。
- 全部应用文案使用中文；用户自行输入的名称和内容保持原样。图标适度使用，导航和金额语义保留文字标签或中文无障碍名称。
- 沿用暖灰白背景、白色内容、墨绿主操作、少量柔和暖橙；收入偏红、支出深青绿。优先整理已有颜色变量，不重新建立不相关的主题。
- 首页保留四个快捷入口的原位置，主要展示本月概览、趋势和紧凑的最近流水，不使用折叠区。今天、本周、本月、本年四条横行保留在独立期间页，右侧支出在上、收入在下。底栏仍为流水、居中突出记一笔、设置；报表等入口保持专项跳转。
- 记一笔的类型横向浏览、金额第一行、自制计算键盘、计算结果与过程、确认直接记账、成功后留在记账页均保留；餐饮和微信的默认仅作用于支出。
- 类别保留大类展开底色、小类无硬边框、合并的“图标”选择入口；新增小类默认收起并用箭头展开／收起。大类名旁的小型改名入口、点击小类编辑、长按排序、返回保留位置继续保留。
- 流水左侧优先账户、其下显示类型，维持原有紧凑尺寸。筛选、完整汇总、按日期分组和已加载浏览位置保持不变。
- 隐私关闭时，首页、净资产、账户、流水和报表等展示路径都不能泄露资金；正在编辑的字段按现有规则处理，不因样式调整改写真实数值。
- 不改记录、账户、类别、图标编号、排序、隐藏项、存储键或备份格式；不改变押金、转账、基金、退休金等已确认规则。真实用户账本不用于破坏性实验。

阶段 0 的原型是接下来第一项交付，不在制定本路线的本轮直接制作。阶段 1 从首页开始，阶段 2、3 分开交付，避免同时改变多个核心操作面。

发现保存失败、数据变动、键盘遮挡或无法返回等阻断问题时，优先于视觉修饰修复。性能若已经阻碍基本操作，可在对应页面阶段提前测量处理；未取得测量证据不增加缓存或虚拟列表。

## 字号、密度和触摸规则草案

以下用于第 0 步原型比较，并非现在直接写进 CSS 的强制替换值。

| 元素 | 候选规则 |
| --- | --- |
| 页面标题 | 约 18–20px，避免巨型标题抢占首屏 |
| 正文和常规选项 | 约 14–16px；紧凑的日期、账本选项可单独比较 12–14px，不通过不断缩字解决拥挤 |
| 辅助信息 | 约 12–13px；关键信息不依赖低对比浅灰 |
| 录入金额 | 约 24–28px，明显大于字段文字；大金额允许适度缩放或换布局，不能截掉尾数 |
| 间距 | 以 4／8／12／16／24 为有限档位；小类和流水保持紧凑，大区块才使用较大间距 |
| 触摸区域 | 主要操作约 48px，紧凑次要入口至少约 44px；视觉图标可更小，但扩大点击区时不能互相覆盖 |
| 文字和状态 | 统一正文／辅助／禁用／选中／错误；收入和支出保留标签；选中类型沿用深色文字和有色底线 |
| 反馈 | 只用短促的状态反馈，不做逐项入场、弹跳、视差或循环背景；尊重减少动画设置 |

系统中文字体继续优先；金额可使用等宽数字特性，不因技能推荐导入展示字体。现有预算、账本、账户和关联选择器继续保持紧凑，不能统一成大弹窗。

## 各页面必须覆盖的状态

- **空状态：** 新账本引导记一笔；类别为空引导新增；筛选无结果可清除条件；报表无数据不伪造图形。
- **编辑与取消：** 编辑区域带出旧值；仅保存时写入；关闭和返回不偷偷保存。非本轮需求不改变已有草稿恢复策略。
- **失败与重试：** 中文提示靠近失败字段；禁止把失败呈现为保存成功；解除重复提交锁并保留输入，保证可修正后重试。
- **返回顺序：** 有临时选择层或键盘时先按既有规则处理当前层，再回到上一页面；类别选择／管理回到来源页，保留浏览位置。首页退出遵守现有原生逻辑。
- **键盘避让：** 数字键盘保留金额、结果与确认功能；原生文字键盘下仍可编辑名称／备注并返回；极矮窗口允许内部滚动，不能盖住返回入口。
- **大字体：** 文字与数值不使用固定高度裁切；允许名称换行、选项纵向重排；底栏标签仍可读，不能只留下无法识别的图标。

## 验证和发布条件

1. 每阶段开始记录当前差异和要改的页面；仅修改本阶段文件与必要文档，不恢复或覆盖无关未提交改动。
2. 使用合成账目覆盖空、常见数量、超长名称、长金额、负收入、隐私、写入失败和跨期关联；与既有结果对照。类别额外比较编号、名称、图标、排序和隐藏项。
3. 预览使用独立来源及合成数据，不连接生产存储。检查 320×640、360×800、390×844、412×915 及 568×320；文字放大检查覆盖 130% 和 200%。这只形成浏览器证据。
4. 有实际 UI 改动时，对改动目标运行一次 Impeccable 静态检测，结果由人或代理结合场景复核。检测器不能证明业务正确、WebView 性能或真机适配，也不因本轮只是写文档而运行。
5. 实施后执行现有 `npm test`、相关 `node --check`、`git diff --check`。需要交付候选包时再执行 `npm run app:build:offline`，记录版本、签名和摘要；本轮不提升版本号。
6. 安装前按 [升级备份检查](UPGRADE_BACKUP_CHECK.md) 和 [设备验收](DEVICE_ACCEPTANCE.md) 执行。继续相同包名、签名及 WebView 来源，不卸载、不清除数据；基金／退休金合法补记与异常数据变化分开核对。
7. 未取得设备授权时继续完成独立原型、桌面验证和代码交付，设备检查保持待办；不把浏览器字号模拟称为 Android 系统字号验收，也不在正式账本上强制崩溃或注入测试数据。

每阶段交付包含改动前后对照、改动位置、验证结果和未验证部分；更新学习记录、问题记录和面试笔记。发布时只推项目代码、必要项目文档和用户明确要求的产物，技能缓存、试验数据和个人学习资料不因本路线自动上传。
