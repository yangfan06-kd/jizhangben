# 离线版稳定性与性能实验（2026-10-11）

本轮以 `com.jizhangben.app` 的现有数据键和 Android 签名为升级边界。记录、账户、类别及图标的存储结构均不迁移；实验使用内存生成的账目，不读取家人手机的数据。

## 已采用的方案

- 流水先筛选全部记录并计算全部收入、支出，然后按日期排序；页面每批绘制 100 笔，用户可继续加载。日期标题与筛选后的总数仍保持完整。未引入多年未更新的 `fast-scroll`。
- WebView 渲染进程崩溃时由 `@capgo/capacitor-webview-crash` 原生重建。定时重启关闭，避免记账过程中意外重载。插件不负责恢复未保存输入，因此新记账表单另存独立草稿；恢复须经用户选择，且不会自动提交成流水。
- Capacitor 8 自带的 SystemBars 负责 Android 安全区域；暂不叠加 `@capacitor-community/safe-area`。当前页面没有启用 `viewport-fit=cover`，原生区域留白和现有 CSS `env()` 配合。须在设备上检查状态栏、底部导航和输入法后才能改变策略。
- 主导航改为实色白底与轻阴影，减少固定区域模糊绘制。继续使用已有的 Tabler SVG 与经典图标编号；页面沿用现有原型的暖灰白、墨绿、收入红和支出深青绿，不整体替换 UI 框架。

## 可重复的合成数据基线

2026-10-17 补充首页和净资产：确认借贷、代付、押金与首页汇总存在重复扫描后，扩展一次同步计算内的临时索引，退出即释放。桌面 Edge 7,800 笔混合账目完整刷新中位数 3,317.2→138.8ms；全部金额与开始源码及独立预期一致。198 项回归、14 项浏览器交互通过，普通收支未建立索引。离线候选包构建与签名／资源核验完成，未安装或推送；真实设备和长期压力仍待验收，详见 [阶段 6 报告](UI_STAGE6_REVIEW.md)。

2026-10-14 补充跨期退款、报销和押金基线：Node 2,700 笔模拟关联账目汇总由原遍历 1,418.21ms 降至临时索引 15.05ms。流水绘制和筛选刷新只在一次同步、只读作用域内复用原账／关联查找，退出即释放，不修改结算公式或存储。浏览器 9,000 笔首批汇总及布局为 17.6ms，金额、实际编辑及删除重算均验证；此浏览器数值没有旧版同条件对照，也不是手机帧率。范围、证据和未优化路径见 `QA_REPORT_1.99.md`。

2026-10-14 补充真实浏览器 DOM 基线，脚本为 `tools/bench-detail-browser.js`，本机预览为 `tools/preview-offline.cjs`。在同一桌面会话、5 万笔普通收支、900 → 1,000 行时，继续加载中位数从 237.85ms 降至 14.15ms；完整刷新并未被替换为缓存。每批仅新增节点、复用当次排序，筛选／数据／绘制代次改变会废弃旧加载事件。所有数据在预览内存生成，存储逐键一致；详细表格、交互证据和限制见 `QA_REPORT_1.98.md`。这仍不是手机帧率，也不包含复杂金融关联性能。

运行 `npm run benchmark:detail`，仅在内存里生成 1千、1万、5万笔模拟记录，测量筛选、排序及取首批 100 笔。2026-10-11 本机一次结果：1千笔 0.75 毫秒；1万笔 7.18 毫秒；5万笔 36.80 毫秒。数值用于后续比较，不代表手机 WebView 绘制或滚动帧率。需要设备测试时，按相同数据量记录冷启动时间、滚动掉帧、占用内存和输入法避让。

## 数据和回退验证

1. 以旧版模拟账本校验升级读取：账目编号、金额、关联关系、类别名称、图标键、排序和隐藏项逐项比较。自动基金/退休金补记如发生，应单独按日期与计划编号核对。
2. 新 APK 只能以相同包名及相同签名覆盖安装，版本号严格增加；不能清除应用数据。`androidScheme: http` 保持不变，确保 WebView 读取同一来源的本地存储。
3. 使用手机前先在应用内导出 JSON 备份，并确认导出文件可解析；实验崩溃使用模拟数据，不能在家人正式账本上触发。
4. 若设备实测有底部遮挡，再单独对比官方 SystemBars 与社区插件。若流水在 5 万笔场景仍有可感知卡顿，下一步采用滚动区域虚拟化，并核对汇总及日期分组。

## 待设备验收

- 崩溃后页面能重新打开；已保存流水保持原样，未保存草稿提示恢复；反复崩溃不会形成无法进入应用的循环。
- 刘海屏、手势导航和三键导航下，顶部、底部、弹层和记账键盘无遮挡、无双重留白。
- 类别长按排序与普通点击编辑仍可区分；流水“再显示”后保留浏览位置；系统大字体下可读。

## 键盘布局检查（2026-10-13）

隔离 568×320 窗口中，旧金额键盘高 302px、顶部只有 18px，覆盖返回入口；页面底部仍留白 380px。新版保留顶部至少 56px，键盘最多 264px，可内部滚动，页面留白按测得高度加 12px 计算。320×640、文字放大 130% 时，键盘高 302px、留白 314px，数字按键最小高 46px，没有整页横向溢出。ResizeObserver 在字体、计算式与可见高度改变时更新留白；旧 WebView 使用显式开关、输入更新及窗口 resize 回退。

浏览器还发现同一金额字段重新聚焦会把 `12+3` 换成 `15`，已保留同字段未确认的计算式；切到本金或余额字段仍读取对应字段值，不把不同金额混用。最终 168 项测试通过，含无观察器回退、动态高度、收起清理、再聚焦及跨字段检查。没有启动或操作手机账本；安全区域和系统大字体仍待用户验收。

## 草稿生命周期检查（2026-10-13）

用户已确认 1.94 的上一轮手机手动测试没有问题；下一轮把原先统一延后执行的草稿捕获拆开：输入和选择即时保存，按钮继续延后至状态修改完成；隐藏页面和 pagehide 再补存一次。新建表单的草稿仍用 `record-form-draft-v1`，不修改账目、类别、账户的键或原生插件配置。模拟重载、后台、编辑旧流水及存储失败已加入回归；这些不是实际渲染进程崩溃测试。进程突然终止未必触发生命周期事件，因此主要依靠每次输入已持久化，不能保证存储不可用时仍可恢复。

用户随后授权自动检测，已在独立手机检测包执行一次真实渲染崩溃，原生记录 `renderProcessGone`、`didCrash=true`，首页重建、恢复确认及草稿字段均检查通过；原模拟记录和配置不变。正式应用数据快照前后字节一致，检测副本已删除。详细条件、SDK 日志与验证限制见 `QA_REPORT_1.95.md`；没有进行长期性能或多机型压力测试。

## 流水往返检查（2026-10-13）

进入流水时原实现统一调用刷新函数，加载到第二批再往返也退回 100 笔。新实现离开前记录内存浏览状态，回到相同账本／筛选再恢复加载数量及滚动位置；主动刷新、换筛选或账本重置时失效。相对日期边界参与比较，避免跨天复用“今天”的旧范围。

375×812 隔离浏览器中 1,000 笔模拟数据，加载 200 笔后经设置页或模拟原生返回首页，再进入仍为 200 笔、7436px，完整汇总仍为收入 250 元／支出 750 元。搜索后重置首批，隐私遮挡可见，导航和搜索不写存储。175 项回归通过；未运行手机安装、五万笔 DOM 帧率或虚拟化实验。位置不跨应用重启保存。详细证据及限制见 `QA_REPORT_1.96.md`。
