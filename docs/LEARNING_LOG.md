## 第 2 步：明确押金的统计口径

- 日期：2026-09-11
- 目标：保证押金不会被误算为收入或支出。
- 学到的知识：资金流向和损益统计是两个不同维度；押金会改变账户余额，但不代表赚到或花掉了钱。
- 实际完成：将四种押金方向统一为中性统计，只保留进入账户或离开账户的资金流向；押金仍会显示在明细中，但不进入收入、支出和统计图。
- 验证方式：检查 `incomeEffect`、`expenseEffect`、明细颜色和账户余额计算；JavaScript 语法检查和 Git 差异检查通过。
- 遇到的问题：原有逻辑把主动收押金归到收入侧、主动付押金归到支出侧，完整退回时再反向抵消，容易造成收入和支出统计失真。
- 解决方法：把押金定义为中性类型，单独使用 `flow` 字段计算账户余额。
- 面试表达：我区分了现金流和损益口径，避免把资产负债变动错误计入收入或支出。
- 后续疑问：是否需要在界面上单独增加“押金/往来”统计，展示当前仍未收回的押金。

## 第 3 步：增加押金对账和差额结算

- 日期：2026-09-11
- 目标：支持“付出 1000 元押金，最终只收回 700 元”的真实场景。
- 学到的知识：单独记录两笔资金流还不够，还需要用关联 ID 表达业务对应关系；最终差额属于损益，才应该进入收入或支出。
- 实际完成：退回押金时可以选择原始押金记录；勾选最终结算后，系统按原押金金额减去累计退回金额计算差额。
- 计算规则：付押金 1000、退回 700，账户余额净减少 300，支出统计增加 300；全额退回则差额为 0。
- 验证方式：通过 JavaScript 语法检查和 Git 差异检查；还需要在浏览器中完成完整操作验证。
- 遇到的问题：原数据结构没有押金之间的关联字段，无法判断 700 元退回对应哪一笔 1000 元押金。
- 解决方法：为退回记录增加 `depositLinkId` 和 `depositFinal`，保留原始资金流，同时只在最终结算记录上计算差额。
- 面试表达：我把押金建模为“资金流 + 业务关联 + 最终结算”，处理了部分退回和多次退回场景，避免把押金本金误计入损益。
- 后续疑问：需要补充浏览器测试，验证多次退回、删除原押金和编辑结算记录时的行为。

## 第 52 步：建立安全修改账目 API

- 日期：2026-09-15
- 目标：让用户可以更正普通账目的金额、日期、账户、类别、类型和备注，同时不破坏已经完成的押金结算关系。
- 学到的知识：更新接口不能绕过创建接口的领域规则；最可靠的做法是把路径 ID 固定为原记录身份，构造新的待校验对象并复用同一套校验。涉及多条记录的业务关系需要定义锁定边界，而不是只验证单行字段。
- 实际完成：新增 `PUT /api/books/{book_id}/records/{record_id}`，请求体复用创建账目结构，更新时重新验证账本归属、类别、类型、账户和押金规则，并设置新的更新时间。已被退回记录引用的原押金返回 `deposit_record_in_use`，已关联原押金的退回记录返回 `deposit_settlement_locked`。
- 验证方式：后端测试从 64 项增加到 67 项，覆盖正常修改、无效修改不改变原数据、原押金和退回记录两端锁定；前端 17 项回归测试全部通过。真实 HTTP 验证中，同一 UUID 账目成功从 1200 分“日常支出”更新为 5600 分“兼职收入”。
- 遇到的问题：如果先读取记录再只更新用户传入的几个字段，容易遗漏字段组合校验，也会让旧押金字段和新类型不匹配；更严重的是，修改押金结算链路的一端可能让另一端的方向关系失效。

- 兼容策略：业务接口带有效会话时按会话用户隔离数据；无 Cookie 时暂时回退固定开发用户，带无效 Cookie 则返回 401，等网页登录页接入后再关闭回退。
- 验证方式：新增 5 项认证接口测试，覆盖注册自动登录、当前用户、密码错误、退出、无效 Cookie、重复邮箱和关闭开发回退；认证/迁移相关测试 18 项通过，完整后端回归 97 项，前端 48 项保持通过，并新增登录用户空账本读取测试。
- 遇到的问题：已有 91 项后端测试和旧数据库都依赖 schema v4 与固定开发身份，直接强制登录会让旧页面和迁移测试同时失效。
- 解决方法：用版本化迁移增量增加认证表结构；请求依赖优先识别会话，暂时保留可由 `JIZHANGBEN_ALLOW_DEV_FALLBACK` 关闭的“无 Cookie 才回退”兼容开关，并为无效 Cookie 单独返回 401，避免伪造身份继续使用开发用户。
- 面试表达：我用 PBKDF2 加盐哈希和只存摘要的会话表建立认证基础，再把用户解析集中在请求依赖中；通过兼容开关分阶段替换固定身份，避免认证迁移一次性破坏已有数据和接口。
- 后续疑问：网页已经接入登录/注册界面，下一步是在确认真实用户数据可迁移和可恢复后关闭开发用户回退。

## 第 70 步：统一处理会话过期

- 日期：2026-09-15
- 目标：当登录 Cookie 过期或被服务端撤销时，让网页立即退出服务端数据状态，并给用户明确的重新登录提示。
- 实际完成：请求层保留 HTTP 状态码；受保护接口返回 401 时调用统一处理函数，清除当前用户和认证状态，恢复启动时的 localStorage 快照，刷新页面状态并显示“登录状态已过期，请重新登录”。登录、注册、当前用户和退出接口自己的 401 仍留在认证表单中处理，避免把密码错误误判成会话过期。
- 后端验证：把测试会话的 `expires_at` 改为过去时间后访问业务接口，确认返回 `authentication_required`，并确认过期会话记录已经从数据库清理。
- 前端验证：模拟受保护接口返回 401，确认页面状态变为 `guest`、用户信息被清空、本地快照恢复、登录过期提示出现。
- 遇到的问题：读请求失败原本只会静默回退本地，页面可能仍显示“已登录”；同时认证接口自己的 401（密码错误）不能触发全局退出逻辑。
- 解决方法：在请求层按路径排除 `/auth/*`，只对受保护接口的 401 通知认证模块；认证模块再统一清理会话状态和恢复本地数据，避免每个业务表单各写一份过期处理。
- 面试表达：我把 401 当作跨模块的会话状态变化处理，而不是普通网络异常；请求层统一发出事件，认证模块负责清理状态和恢复快照，既保证用户提示一致，也避免密码错误触发误退出。
- 后续疑问：如何在完成迁移演练、备份恢复和网页登录验收后，把 `JIZHANGBEN_ALLOW_DEV_FALLBACK` 默认关闭。

## 第 87 步：修复 App 注册接口返回 HTML 的问题

- 日期：2026-09-17
- 目标：让 App 内的注册请求真正到达 FastAPI，而不是被 Capacitor 内置静态页面截获。

- 验证方式：前端测试 53 项全部通过；后端健康检查返回 200，CORS 预检返回 `Access-Control-Allow-Origin: http://localhost` 和允许凭据；新版 APK 构建、安装成功，用户在真实小米手机上完成注册。
- 关键知识：App 的“页面能打开”与“API 能访问”是两条链路；`localhost` 在手机上默认指向手机自身，USB reverse 才能把它映射到电脑。跨端口请求还需要 CORS 和 Cookie 凭据配置，开发 HTTP 通道不能直接当作生产 HTTPS 方案。

- 目标：在 Docker Desktop 启动失败时恢复本地记账本容器，同时保护已有 SQLite 数据卷。

- 解决方法：先确认 Docker 进程全部停止，再把只包含临时 socket 的 `AppData\Local\Docker\run` 和 `AppData\Local\docker-secrets-engine` 目录改名保留备份，创建空的同名目录后以正常系统权限重新启动 Docker Desktop。没有删除 `G:\DockerData`，也没有执行 Docker 的恢复出厂操作。
- 验证方式：Docker 引擎恢复并报告 Server `29.8.0`；`jizhangben-app-1` 状态为 `Up (healthy)`，端口映射为 `0.0.0.0:8000->8000/tcp`；`/api/health` 返回 `{"status":"ok","database":"ok","schema_version":5}`；Git 工作区没有代码改动。
- 关键知识：Docker 的临时运行 socket 与容器卷是两类数据，排障时应先按日志定位具体运行目录，只替换无法释放的临时目录，不能把“重置 Docker”当成默认修复方式。
- 面试表达：我根据后端日志把故障从应用层缩小到 Windows AF_UNIX 临时 socket，保留原目录作为回退证据，用容器健康检查、API 数据库状态和 Git 工作区三层结果验证恢复没有破坏业务数据。
- 下一步：继续准备真实 HTTPS 域名和服务器，完成移动网络登录、离线恢复、同步和会话过期验收。

## 第 111 步：演练 Docker 数据卷备份与恢复

- 目标：在正式 HTTPS 部署前确认 SQLite 数据卷可以独立备份，并能恢复到新的卷中继续读取。

- 关键知识：运行中的 SQLite 不应直接复制可能带有未合并 WAL 的文件；使用 SQLite backup API 可以在服务继续运行时生成一致副本，恢复演练还要在独立卷中验证，而不是只检查备份文件存在。
- 面试表达：我把数据库备份拆成“在线生成一致副本—恢复到隔离卷—查询结构和业务数量”三步，用实际记录数量证明恢复结果可读，而不是只看压缩包是否生成。

## 第 112 步：把在线备份接入部署脚本

- 目标：让 Docker 部署环境可以用一条可复用命令生成数据库备份，减少手工复制正在运行的 SQLite 文件的风险。
- 实际完成：新增 `deploy/backup-volume.ps1`，默认读取 `jizhangben_jizhangben-data` 卷，使用应用镜像中的 Python 和 SQLite backup API 生成带时间戳的 `.db` 文件，并输出 schema、文件大小和 SHA-256；备份目录加入 Git 忽略。
- 遇到的问题：PowerShell 直接把多行 Python 代码传给 Docker 时，Windows 原生命令参数会移除代码中的引号，导致脚本在容器内解析失败。
- 解决方法：把 Python 辅助代码临时写入备份目录并挂载到容器，执行结束后立即删除辅助文件；这样保留了跨 Windows、Docker 和 Python 的清晰边界，也避免把临时脚本提交到备份目录。
- 验证方式：对当前运行中的正式卷执行脚本，成功生成 147456 字节的备份，schema 为 5，完整性检查通过，SHA-256 为 `45CF34365D31293F9767AC47529A26194BD63AA823C7B20A86C231C4D7D36939`；测试输出目录随后清理，应用容器和数据库健康状态保持不变。
- 关键知识：部署脚本不仅要“能生成文件”，还要在脚本内完成卷存在性检查、SQLite 完整性检查和校验和输出，并把备份文件明确排除在 Git 和应用镜像之外。
- 面试表达：我把一次成功的恢复演练沉淀成可重复脚本，处理了 Windows 原生命令转义、Docker 卷挂载和 SQLite 在线备份三个边界，并用真实运行卷验证脚本结果。

## 第 114 步：增加 HTTPS 部署预检

- 目标：拿到真实域名和服务器后，先一次性检查生产配置，再启动 Caddy 和应用，避免把开发地址或不安全 Cookie 带入发布环境。
- 实际完成：新增 `deploy/preflight.ps1`，检查域名格式、`http://localhost` App 来源、`SameSite=None`、Secure Cookie、关闭开发回退、本机端口绑定、Compose 配置和正式 HTTPS API 地址；检测到 Caddy 时还会校验 Caddyfile。
- 遇到的问题：当前本机没有真实域名和 Caddy，不能把 DNS 和证书检查伪装成已完成；同时生产预检不能修改当前局域网容器的环境变量。
- 解决方法：预检只解析指定的 env 文件，在独立子进程中运行 Compose 和 API 地址检查；`-SkipDns` 允许在服务器 DNS 尚未切换时先验证其余配置，并明确报告 Caddy 检查是否跳过。
- 验证方式：用临时 `ledger.test` 配置运行预检，Compose 检查、HTTPS `/api` 地址检查均通过，DNS 按参数跳过，未启动生产服务；`deploy/.env` 已加入 Git 忽略，避免真实配置进入仓库。
- 关键知识：生产预检应把“配置格式正确”“DNS 已解析”“Caddy 已安装”“HTTPS 服务已可访问”拆成不同证据，不能用其中一项替代全部上线条件。
- 面试表达：我把部署前的安全边界编码成可失败的 PowerShell 预检，区分静态配置、工具存在性和外部 DNS 条件，让正式部署可以按证据逐层推进。
- 下一步：准备真实 HTTPS 域名和服务器后，运行完整预检，启动 Caddy，再用 HTTPS 健康接口、登录会话和 APK 读取完成移动网络验收。
