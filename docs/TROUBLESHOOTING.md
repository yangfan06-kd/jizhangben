### 单文件代码规模较大

- 发现时间：2026-09-10
- 现象：`index.html` 同时包含页面结构、样式、状态管理、数据存储、业务计算和图表渲染。
- 影响：修改一个功能时不容易判断影响范围，测试和多人协作也比较困难。
- 原因：项目从单文件原型逐步增加功能，没有及时进行模块化。
- 解决：第一阶段按职责拆分文件，并每次拆分后验证原有功能。
- 验证：拆分完成后检查记账、账户、账本、筛选、统计和备份功能。
- 预防：新功能先放入对应模块，避免继续把所有代码添加到入口文件。
- 面试表达：我识别出单体前端文件带来的维护风险，采用渐进式重构，降低一次性重写的风险。

### 押金部分退回无法反映实际损失

- 发现时间：2026-09-11
- 现象：支付 1000 元押金后只退回 700 元，原来的数据结构只能记录两笔独立流水，无法知道 300 元是押金扣款。
- 影响：押金本金可能被错误计入收入或支出，或者损失金额无法进入支出统计。
- 原因：缺少原始押金与退回记录之间的关联，也没有最终结算状态。
- 解决：退回记录关联原始押金；最终结算时按原押金金额减去累计退回金额计算差额。
- 验证：需要测试全额退回、部分退回、多次退回和另一方向的押金收取后部分退还。
- 预防：涉及往来业务时同时设计资金流、关联关系和结算状态，不只保存金额和类型。
- 面试表达：我通过关联记录和结算状态解决了部分退款的业务建模问题。

### 浏览器自动化测试缺少 npm/npx

- 发现时间：2026-09-11
- 现象：系统可以运行 Node.js，但找不到 npm 和 npx。
- 影响：暂时不能使用 Playwright 对手机和桌面页面执行真实交互测试。
- 原因：当前环境只有 Node.js 可执行文件，npm 工具链没有加入环境。
- 解决：安装 Node.js 的完整版本或 npm，并确认 `node --version`、`npm --version` 和 `npx --version` 都能运行。
- 验证：安装后重新执行押金对账的浏览器场景测试。
- 预防：在项目测试说明中记录 Node.js/npm 版本要求。
- 面试表达：遇到自动化测试环境缺失时，先区分代码问题和环境问题，保留静态验证结果并补齐运行环境。

### Playwright 默认 Chrome 不可用

- 发现时间：2026-09-11
- 现象：Playwright 启动时找不到 Chrome 安装路径。
- 影响：不能直接打开页面执行自动化操作。
- 原因：机器上没有 Chrome，但已有 Microsoft Edge。
- 解决：让 Playwright 使用 Edge，并通过本地 HTTP 服务访问项目页面。
- 验证：押金对账端到端场景通过；浏览器临时数据已清除。
- 预防：在测试环境说明中记录可用浏览器和启动方式。
- 面试表达：测试工具遇到浏览器依赖问题时，我切换到现有兼容浏览器，并保持测试目标不变。

### Playwright 下拉框操作命令名称不同

- 发现时间：2026-09-12
- 现象：尝试使用 `select-option` 操作账户下拉框时，命令行提示未知命令。
- 影响：一次测试操作没有执行，不能据此判断页面保存失败。
- 原因：当前 Playwright CLI 使用 `select` 命令，而不是其他自动化工具中常见的命令名称。
- 解决：改用 `select` 选择账户后重新点击保存，确认记账和视图渲染正常。
- 验证：12 元支出成功保存，统计卡片、明细列表和账户余额均同步更新；随后通过页面删除临时记录。
- 预防：执行自动化操作前先查看当前 CLI 的帮助信息，确认命令名称和参数格式。
- 面试表达：我会区分测试工具操作失败与产品功能失败，先确认测试命令本身有效，再判断应用行为。

### 关键字筛选后汇总没有同步

- 发现时间：2026-09-12
- 现象：输入关键字后，明细按钮显示 1 笔，但收入、支出汇总和统计图仍包含未匹配的记录。
- 影响：用户看到的列表和统计结果不一致，容易误判当期收支。
- 原因：搜索输入事件只调用了 `renderList()`，没有触发汇总和图表刷新。
- 解决：将搜索输入事件改为调用统一的 `refreshDetail()`，让列表、汇总和图表共享同一组筛选结果。
- 验证：搜索“早餐”后支出从 25 元变为 5 元，切换“交通”后变为 20 元，两个结果都与列表一致。
- 预防：所有会影响查询结果的控件都调用统一刷新入口，并为列表与统计同时变化的场景保留浏览器测试。
- 面试表达：我通过端到端验证发现多个视图使用了不同刷新路径，随后统一事件入口，修复了查询结果不一致的问题。

### 刷新后自定义选项看起来消失

- 发现时间：2026-09-12
- 现象：新增自定义类型后刷新页面，折叠状态下只看到前五个内置类型，旧的展开按钮引用也无法继续点击。
- 影响：容易误以为自定义类型没有保存，或把自动化引用失效误判为页面功能故障。
- 原因：类型列表默认折叠，只显示 `COLLAPSE_COUNT` 项；页面刷新后 DOM 重新生成，之前的元素引用已经失效。
- 解决：重新获取当前页面快照中的展开按钮，再展开列表；确认自定义类型从 localStorage 重新加载并显示。
- 验证：刷新后展开列表可见“临时类型”；删除该类型后列表恢复为内置选项。
- 预防：测试中把“刷新后的持久化恢复”和“折叠列表展开”分开验证，每次重绘或刷新后重新获取控件引用。
- 面试表达：我把持久化问题和测试引用问题分开定位，先验证数据是否恢复，再验证重新渲染后的交互是否可用。

### 配置拆到独立脚本后页面初始化失败

- 发现时间：2026-09-12
- 现象：如果 `constants.js` 在使用配置的模块之后加载，页面启动时可能找不到键名、默认账户或押金方向。
- 影响：数据读取、账户下拉和押金表单可能在初始化阶段报错。
- 原因：当前项目使用多个传统脚本，脚本标签顺序决定了声明何时进入页面的全局作用域。
- 解决：让 `constants.js` 作为第一个业务脚本加载；其他模块只在函数被调用时使用这些配置。
- 验证：HTTP 服务日志显示 `constants.js` 成功返回 200；Edge 页面正常加载默认账户，记账、明细和图表流程均通过。
- 预防：新增脚本时先画出加载依赖顺序，并在页面回归中检查资源请求和首次渲染。
- 面试表达：我把脚本加载顺序当成前端依赖的一部分管理，先加载稳定配置，再加载存储、计算和交互模块。

### 切换账本后筛选条件残留

- 发现时间：2026-09-12
- 现象：从一个账本切换到另一个账本后，明细搜索框或日期/类别下拉仍保留上一个账本的条件。
- 影响：新账本明明没有记录，页面却可能显示“没有结果”，用户容易误以为数据丢失。
- 原因：筛选值分散在多个变量中，账本切换时容易漏清其中一个；只清理内存值也不会自动清空输入框。
- 解决：用 `filterState` 集中保存筛选值，统一调用 `resetFilterState()`，同时清空日期输入、下拉框和搜索框。
- 验证：在主账本输入关键字后切换临时账本，确认筛选控件全部为空；删除临时账本和记录后主账本统计恢复正常。
- 预防：所有跨账本切换、备份导入等重载入口都调用统一的状态重置函数，并同步更新 DOM。
- 面试表达：我通过集中状态和统一重置入口，修复了跨页面切换时的旧筛选残留问题。

### 编辑记录后保存成了新记录

- 发现时间：2026-09-12
- 现象：进入编辑页面后，如果编辑 ID 没有被正确保存，点击保存会走“新增”分支，账目数量会多出一笔。
- 影响：用户修改一笔账时可能产生重复记录，金额统计也会被重复计算。
- 原因：编辑 ID 原来是入口脚本中的独立变量，表单模块和其他模块共享时容易遗漏或被重置。
- 解决：把编辑 ID 统一放在 `uiState.editingRecordId`，保存时根据它判断新增还是修改；`resetForm()` 统一将它恢复为 `null`。
- 验证：12.34 元临时记录进入编辑后金额和备注正确回填，点击取消后没有新增记录；随后删除原记录，统计恢复为 0。
- 预防：编辑流程至少验证“进入编辑、取消、保存修改”三个分支，并确保清空表单时同步清空编辑状态。
- 面试表达：我用显式编辑状态区分新增和修改路径，避免表单操作产生重复数据。

### 删除当前账本后刷新仍指向旧账本

- 发现时间：2026-09-12
- 现象：删除当前账本后页面暂时显示正常，但刷新时可能仍使用已删除账本的 ID 读取数据。
- 影响：账本下拉选择、账目读取和账户读取可能出现空数据或状态错乱。
- 原因：当前账本 ID 同时存在于内存变量和 localStorage；删除时只更新其中一处会留下过期上下文。
- 解决：把当前账本 ID 统一放入 `dataState.currentBookId`，删除当前账本时先回退到剩余账本，再同步写入 `CURRENT_BOOK_KEY`。
- 验证：创建并切换临时账本后删除，顶部下拉自动回到“我的账本”，刷新页面仍保持正确选择。
- 预防：所有读写当前账本的代码都通过 `dataState.currentBookId`，并为切换、删除和刷新保留回归流程。
- 面试表达：我统一了运行时上下文和持久化上下文，修复了删除当前实体后页面仍引用旧 ID 的问题。

### 账目状态迁移后新增记录不见了

- 发现时间：2026-09-12
- 现象：把账目数组迁移到 `dataState.records` 后，如果某个模块仍写入旧变量，页面统计和明细可能读取不到新记录。
- 影响：保存提示显示成功，但账目列表、余额或图表没有变化。
- 原因：迁移数组时同时存在旧变量和新对象，读写路径不一致。
- 解决：删除入口脚本中的旧 `records` 声明，并统一把读取、`push`、筛选、删除和保存改为 `dataState.records`。
- 验证：新增 7.89 元支出后首页、明细和图表均显示该记录；刷新后仍显示；删除后统计恢复为 0。
- 预防：状态迁移前先全文列出所有读写点，迁移后检查旧变量是否仍存在，再执行新增、刷新和删除回归。
- 面试表达：我通过消除双重数据来源，保证写入和读取始终指向同一个状态对象。

### 账户列表和净资产计算不一致

- 发现时间：2026-09-12
- 现象：新增或删除账户后，账户页的列表发生变化，但首页净资产或记账页账户下拉没有同步。
- 影响：用户看到的账户信息与实际余额计算不一致，新增账户也可能无法被记账使用。
- 原因：账户数组原来由入口脚本维护，余额计算、下拉渲染和账户管理可能分别读取不同引用。
- 解决：将账户数组统一放入 `dataState.accounts`，存储、余额计算、负债判断、下拉和账户管理全部使用该对象。
- 验证：新增本金 50 元的“状态账户”后净资产变为 50 元，记账下拉出现该账户；删除后净资产回到 0，默认账户仍完整。
- 预防：账户相关改动同时检查列表、下拉、余额和删除流程，避免只验证一个页面。
- 面试表达：我统一了账户数据的读取边界，确保展示、选择和计算结果来自同一份状态。

### 编辑账户或账本后变成新增

- 发现时间：2026-09-12
- 现象：进入账户或账本编辑表单后点击保存，可能生成重复项，或取消后下一次操作仍带着旧对象。
- 影响：账户余额、账本列表和后续选择会出现重复数据，用户难以判断哪一项才是最新版本。
- 原因：编辑 ID 原来是入口脚本中的独立变量，表单模块重绘或重置时容易遗漏；新增和修改分支缺少统一的编辑上下文。
- 解决：把账户和账本编辑 ID 分别放入 `uiState.editingAccountId`、`uiState.editingBookId`；进入编辑时写入 ID，保存后或取消时由对应 reset 函数清空。
- 验证：临时账户 10 元改为 20 元后列表只有一项且净资产为 20 元；取消修改不会保存输入值；临时账本修改名称和分类后只有一项，取消修改也不会产生重复账本；删除测试数据后净资产回到 0。
- 预防：每个可编辑实体至少覆盖进入编辑、保存修改、取消修改和删除四个分支；页面重绘后重新获取控件引用，并检查编辑 ID 是否已重置。
- 面试表达：我用显式编辑上下文区分新增和修改，修复了表单重绘后状态丢失导致的重复数据问题。

### 新增自定义类别后筛选下拉不更新

- 发现时间：2026-09-12
- 现象：自定义类别按钮立即出现，也能被选中，但明细页的类别筛选下拉暂时没有这一项。
- 影响：用户可以记账，却不能马上用筛选下拉查询刚新增的类别，页面不同区域给出的选项不一致。
- 原因：新增逻辑只重绘了类别按钮，没有调用负责重建筛选下拉的 `fillCategoryFilter()`。
- 解决：把类别新增后的刷新路径补成“更新 `dataState.customCategories`、保存 localStorage、重绘按钮、刷新筛选下拉”。
- 验证：新增“状态类别筛选”后切换明细页，下拉立即出现该选项；刷新页面仍能看到；删除后下拉同步移除。
- 预防：每个共享状态变更都检查依赖它的所有视图，并为新增、刷新、删除三个阶段保留回归验证。
- 面试表达：我定位到数据状态已更新但视图刷新入口遗漏的问题，补齐统一刷新流程，避免同一状态在不同控件中显示不一致。

### 拆出工具模块后页面初始化失败

- 发现时间：2026-09-12
- 现象：如果 `helpers.js` 放在存储或业务模块之后，页面启动时可能找不到金额规范化、日期或类型判断函数。
- 影响：账目和账户无法读取，或者首次渲染在进入页面时直接报错。
- 原因：传统脚本按标签顺序执行，函数虽然只在后续调用，但声明必须先进入页面的全局作用域。
- 解决：把通用工具放在 `constants.js`、`state.js` 之后，`storage.js` 之前；工具模块只声明函数，不在脚本加载阶段操作 DOM。
- 验证：HTTP 服务中 `helpers.js` 返回 200；页面能新增 3.21 元支出、显示明细并删除恢复；控制台只剩开发服务器缺少 `favicon.ico` 的 404。
- 预防：新增脚本前先列出它读取的常量、状态和函数，按依赖顺序加载，并用首次打开页面和一条真实数据流程回归。
- 面试表达：我把脚本标签顺序当作前端依赖管理的一部分，先加载声明再启动应用，避免模块拆分造成初始化回归。

### 押金退回保存失败

- 发现时间：2026-09-12
- 现象：已填写退回金额、对象、原押金和最终结算，但点击保存没有新增记录。
- 影响：用户可能误以为押金关联或最终结算功能失效。
- 原因：押金属于资金流类型，仍然必须选择资金或负债账户；账户下拉没有选择时会被统一校验拦截。
- 解决：补选账户后再保存；保留 `needsAccount` 校验，避免产生没有资金归属的押金记录。
- 验证：1000 元主动支付、700 元关联退回并最终结算后，支出和净资产均为 -300；删除测试记录后恢复为 0。
- 预防：押金测试清单同时包含方向、对象、原押金、账户和最终结算勾选，不能只验证金额提示。
- 面试表达：我把表单校验失败定位为缺少必要账户，而不是误判为模块拆分问题，并保留统一校验确保资金流有明确账户。

### 新增账户后下拉选项不更新

- 发现时间：2026-09-12
- 现象：账户列表已经出现新账户，但记账页账户下拉或明细页账户筛选仍没有这一项。
- 影响：用户无法在新账户中记账或按新账户查询，页面显示与实际数据状态不一致。
- 原因：新增账户只更新了 `dataState.accounts` 和账户列表，没有调用负责重建下拉选项的统一渲染函数。
- 解决：把账户下拉生成集中到 `js/selects.js`，新增、编辑、删除账户后通过 `renderAccountSelects()` 同步记账下拉和明细筛选；类别筛选同样通过 `fillCategoryFilter()` 更新。
- 验证：新增本金 12.34 元的临时账户后，两个账户下拉均出现；新增临时类别后明细类别筛选出现；删除测试数据后净资产回到 0。
- 预防：共享状态变化后，同时检查依赖它的列表、表单和筛选控件；每次页面重绘后重新获取控件引用。

### SQLite 的 INTEGER 列仍接受小数本金

### 外键有效但账目引用了其他用户的数据

- 发现时间：2026-09-14
- 现象：类别、记账类型或账户 ID 在数据库中真实存在，普通外键检查会通过，但这些对象可能属于另一用户或另一账本。
- 影响：账目会跨越用户和账本边界，导致数据泄露、余额错误和手机电脑同步后的权限问题。
- 原因：单列外键只验证目标主键存在，不理解“当前账本的所有者”和“账户所属账本”等业务关系。
- 解决：服务层先由账本确定 `user_id`，类别和类型按 `(id, user_id, 未归档)` 查询，账户按 `(id, book_id)` 查询；任何一步失败都抛出稳定业务错误并回滚事务。

- 预防：多租户系统的每个资源查询都携带所有权边界，不能先按全局 ID 查询再假设它属于当前用户。
- 面试表达：我通过负向测试证明“外键存在”不等于“用户有权使用”，随后在服务层把账本所有者贯穿到所有关联查询中，阻止跨租户写入。

### API 的字段错误和业务错误结构不一致

- 发现时间：2026-09-14
- 现象：FastAPI 默认的请求校验错误使用 `detail` 列表；业务层若通过 `HTTPException(detail={...})` 抛出，稳定错误代码又会嵌套在另一个 `detail` 中。
- 影响：网页和手机端必须判断多种响应形状，容易出现后端已经给出原因但界面只显示“请求失败”。
- 原因：框架字段校验与项目业务异常来自不同层，默认没有共享响应契约。
- 解决：分别注册请求校验和账目业务异常处理器，根级统一返回 `code` 与 `message`，请求字段问题额外返回 `details`。
- 验证：接口测试分别触发 404、409 和三种 422，断言状态码、根级错误代码、中文提示与字段详情；成功响应继续返回 201。
- 预防：新增业务模块时复用同一错误响应模型和异常映射，不在各路由中临时拼接不同 JSON。
- 面试表达：我统一了框架校验错误和领域错误的 API 契约，使不同客户端只依赖稳定代码，同时保留字段级调试信息。

### 删除账本时不应误用账户删除的历史保留策略

### 备份导入不能直接按原 ID 写回数据库

- 发现时间：2026-09-15
- 现象：备份里的账本、账户和账目 ID 可能来自另一台设备或旧数据库，直接写回会和现有数据冲突，也无法安全处理转账与押金关联。
- 影响：导入可能部分成功，或把新数据错误地关联到旧账本，造成串账。
- 原因：外部备份 ID 只是来源标识，不是当前数据库的授权身份；关系数据还存在父子顺序和自关联依赖。
- 解决：先完整校验备份和所有跨表关系，再为每类来源 ID 生成新的 UUID；按账本、账户、选项、账目的顺序写入，押金记录按 `deposit_link_id` 依赖顺序插入。
- 验证：真实 HTTP 闭环中，导出后增加干扰账本再导入，旧 ID 被映射为新 UUID，账目和净资产保持一致；非法引用在删除旧数据前返回 `backup_invalid`。
- 预防：备份格式必须带版本号，导入必须使用事务并返回结构化 `id_map`；在服务端数据确认可读前保留原始备份和 localStorage。
- 面试表达：我把备份恢复设计成版本化、隔离用户、重新映射 ID 的事务流程，避免直接复用外部主键造成冲突或跨账本关联。

### 后端 UUID 不能按数字 ID 处理

- 发现时间：2026-09-15
- 现象：服务端账本和账户已经能显示，但下拉框切换后得到 `NaN`，账户选择也会被当成空值。
- 影响：读取看似成功，新增本地账目却无法绑定服务端账户，编辑和删除按钮也找不到目标。
- 原因：旧前端 localStorage 使用时间戳数字 ID，表单事件曾用 `Number(...)` 强制解析；后端主键是 UUID 字符串。
- 解决：账本、账户和账户引用统一保留原始字符串，查找时用字符串化后的 ID 比较；本地数字 ID 仍然兼容。
- 验证：后端读取映射测试覆盖 UUID，页面事件代码不再将账本、账户下拉值转换为数字，前端测试 22 项全部通过。
- 预防：数据访问层先定义统一 ID 契约，所有外部 ID 默认按不透明字符串处理，只有确实需要数值运算的字段才转换。
- 面试表达：我在渐进迁移时识别出本地数字主键与后端 UUID 的类型差异，把 ID 当作不透明标识处理，避免“列表能读、操作不能用”的半成功状态。

### 直接打开文件与 HTTP 页面不是同一种后端连接环境

- 发现时间：2026-09-15
- 现象：双击 `index.html` 时浏览器没有可用的同源 API 地址；即使后端已启动，网页也不能默认请求 `/api`。
- 影响：如果把网络失败当成页面故障，容易误以为本地数据丢失，或为了联调破坏原有可用流程。
- 原因：`file://` 页面没有 HTTP origin；跨端口访问还会受到浏览器同源和 CORS 规则影响。
- 解决：后端读取层检测页面协议，`file://` 直接停用请求；HTTP/HTTPS 页面默认使用 `/api`，请求失败或返回空账本时保留 localStorage 数据，并在成功读取后提示当前仍是“后端读、本地写”。
- 验证：API 客户端测试覆盖文件模式停用、HTTP 请求映射、空响应回退、账户读取和失败恢复；完整前端测试 22 项通过。
- 预防：先确定页面访问方式和 API 基地址，再做网络联调；迁移阶段始终保留本地备份和可回退数据源。
- 面试表达：我把运行环境差异作为数据访问层的职责，采用异步尝试、明确回退和可读提示，让后端联调不会阻塞原有本地功能。

### 多个后端读取接口不能分别替换页面状态

- 发现时间：2026-09-15
- 现象：账本列表先切成服务端数据，账户或明细接口随后失败时，页面可能同时混用服务端账本和本地账户；当前账本统计与跨账本总览也会出现不同口径。
- 影响：用户看到的页面像是加载成功，但不同面板来自不同数据源，新增或切换操作难以判断实际作用对象。
- 原因：账本、选项、账户、明细和总览是相互依赖的一组快照，分别异步写入状态会留下半迁移状态；服务端系统选项还会和前端内置选项重复。
- 解决：启动前保存整组 localStorage 快照，依次校验所有响应后一次性渲染；任一请求失败就整体恢复。总览改用服务端摘要，选项只映射非系统项为自定义数据。
- 验证：前端测试覆盖自定义选项过滤、明细和押金方向映射、总览金额映射、UUID 账户引用、异常明细回退，以及账户读取失败时的整体恢复；完整前端测试 28 项通过，后端 84 项通过。
- 预防：多个资源组成一个页面快照时，先定义切换边界和回退策略，再编写每个接口的适配函数；不要在请求回调里直接覆盖一半状态。
- 面试表达：我把多接口联调视作一次快照提交，使用响应校验、统一渲染和整体回退解决了前后端逐步迁移时的数据源混用问题。

### localStorage 的数字 ID 不能直接作为服务端全局 ID

- 发现时间：2026-09-15
- 现象：两个本地账本都可能有 ID 为 `1` 的“现金”账户，直接转换后会发生重复主键或把账目关联到错误账本。
- 影响：迁移可能在导入阶段失败，也可能在关系未被严格校验时出现串账，账户余额和押金对账都会失真。
- 原因：localStorage 的 ID 只在各账本的键名中局部有意义；服务端备份需要在整个 payload 内唯一，并且还要能表达转账和押金自关联。
- 解决：转换器把来源 ID 作用域化为 `account:<book_id>:<old_id>` 和 `record:<book_id>:<old_id>`，先完成本地关系解析，再交给服务端生成 UUID 和返回 `id_map`。
- 验证：脱敏样本导入后 4 笔账、2 个账户和押金关联全部恢复；同一 payload 的坏账本引用返回 422，原服务端数据保持不变，后端迁移测试 5 项通过。
- 预防：迁移设计中把“来源 ID 唯一范围”和“目标 ID 生成策略”写进契约，不能只看单个 localStorage 数组里的数字是否唯一。
- 面试表达：我先识别旧 ID 的作用域，再设计带作用域的来源标识和目标 UUID 映射，避免把局部主键直接提升为全局主键。

### 迁移预览不能为了计算摘要而覆盖正式数据

- 发现时间：2026-09-15
- 现象：如果网页在用户确认前直接调用替换式导入接口，预览失败或用户取消时，当前服务端账本可能已经被清空。
- 影响：用户无法比较迁移前后的数量和金额，也失去了在确认前撤回的安全边界。
- 原因：正式导入接口的职责是事务式替换数据，预览接口的职责是验证和计算摘要；两者写入权限不同。
- 解决：增加只读的 `/api/backups/preview` 和 `/api/backups/preview-local`，只在内存中完成转换、关系校验和收支计算，返回分账本与总计摘要；真正写入仍由用户确认后调用 `/api/backups/import`。
- 验证：预览脱敏备份后查询服务端账本仍为空，数量、押金少退差额和净资产与导入后的总览一致；后端完整测试达到 90 项。
- 预防：迁移流程固定为“备份本地数据—预览对账—用户确认—事务导入—重新读取验证”，未通过预览不能触发导入。
- 面试表达：我把迁移拆成只读预览和可写导入两个权限边界，避免为了展示结果而提前改变正式数据，并用导入前后同一套金额规则保证对账可解释。

### 服务端写入失败时不能继续使用 UUID 内存快照做本地回退

- 发现时间：2026-09-15
- 现象：后端读取成功后，页面账本和账户使用 UUID；如果新建请求失败仍直接在当前数组上执行本地保存，localStorage 会混入服务端对象，刷新后可能出现没有对应明细的账本。
- 影响：用户看到本地和服务端数据混在一起，后续账目引用可能找不到原来的数字 ID。
- 原因：渐进迁移期间，内存状态和 localStorage 的主键来源不同；“请求失败”不等于可以把服务端快照当作本地快照。
- 解决：后端写入失败时先清除后端读取标记，从 localStorage 重新加载账本、账户、选项、明细和总览，再调用原有本地保存函数；成功写入则只更新当前内存并重新读取服务端总览。
- 验证：单元测试先放入服务端 UUID 账本，再让创建请求抛出网络错误，确认页面恢复原数字 ID 本地账本并保存新账本；前端完整测试达到 33 项。
- 预防：所有渐进迁移写入都要明确“成功状态”和“回退数据源”，不能只把 `backendBooksLoaded` 改成 `false` 就继续复用旧内存数组。
- 面试表达：我把回退设计成一次完整快照恢复，而不是局部换标记，解决了后端 UUID 与 localStorage 数字 ID 并存时的主键污染问题。

### 账目写入回退时需要重新解析账户和押金关联

- 发现时间：2026-09-15
- 现象：服务端读取成功后新建账目请求失败，如果直接把当前记录写入 localStorage，账户会保留服务端 UUID；押金退回记录还可能引用只存在于服务端快照的记录 ID。
- 影响：页面当下看似保存成功，刷新后本地账户余额无法应用，押金最终差额也找不到原押金。
- 原因：后端快照使用 UUID，旧 localStorage 使用各账本自己的数字 ID；两套数据的主键和记录关联范围不同。
- 解决：回退前保存账户名称和原押金的业务指纹，先恢复 localStorage 的完整快照，再按名称和指纹解析本地账户及押金 ID，最后执行本地保存。
- 验证：前端回归测试让服务端账户 `server-cash` 写入失败，确认恢复后的本地记录重新引用数字账户 `7`；普通记录和押金请求测试共 36 项通过。
- 预防：跨数据源写入失败时，不能只切换一个“后端关闭”标记；任何外键都要在目标数据源中重新解析，找不到时应明确提示并停止写入。
- 面试表达：我为渐进迁移的回退路径补充了引用重映射：先恢复目标存储的快照，再用稳定业务字段恢复账户和押金关系，避免跨来源主键直接落库。

### 异步保存要区分创建失败和重新读取失败

- 发现时间：2026-09-15
- 现象：保存账目后重新读取明细的请求可能暂时失败；如果把这个失败当成创建失败再次走本地回退，服务端已经存在的记录会被重复保存。
- 影响：用户可能看到一条服务端记录和一条本地副本，后续迁移时出现重复账目。
- 原因：创建接口和读取接口是两个独立请求，前者成功后不能撤销；同时异步按钮事件不会自动阻止第二次点击。
- 解决：保存期间设置 `recordSaveInFlight` 并禁用按钮；创建成功后保留服务端响应，明细 GET 失败只提示稍后重试，不执行本地回退。
- 验证：测试连续调用两次保存只产生一个 POST，并分别验证创建后的明细 GET；前端 37 项测试全部通过。
- 预防：把写入状态拆成“请求中、创建成功、重新读取成功/失败、创建失败”几个节点，只有真正的创建失败才进入备用存储。
- 面试表达：我把异步写入和读回拆成两个一致性阶段，利用按钮状态阻止重复提交，并避免把读回故障误判为写入失败而制造重复数据。

### 服务端业务冲突不能自动回退成本地账目

- 发现时间：2026-09-15
- 现象：服务端返回带 `code` 的 409/422 业务错误时，如果继续走本地回退，押金关联、账户归属等规则会只在本地被绕过。
- 影响：用户会看到本地有账、服务端没有账，下一次联网或迁移时出现两套结果。
- 原因：网络异常和业务拒绝都表现为请求失败，但前者可以换存储，后者需要用户修正输入。
- 解决：客户端识别服务端错误码；业务冲突保留表单和服务端中文说明，网络类错误才恢复 localStorage 并本地保存。
- 验证：模拟 `deposit_link_not_found` 后，记录数量保持不变、后端读取状态保持开启、表单状态为 `conflict`；前端 38 项测试全部通过。
- 预防：错误处理先区分错误来源，再决定回退、重试或修正，不能把所有 `catch` 都绑定到备用数据源。
- 面试表达：我用稳定错误码把传输层故障与领域校验失败分开，避免为了“保证能保存”而绕过服务端业务边界。

### 服务端删除成功返回 204，页面却提示失败

- 现象：账目删除接口已经在数据库中删除记录，但前端调用 `response.json()` 时因为响应没有内容而抛错，随后错误地走本地回退。
- 原因：`DELETE /api/books/{book_id}/records/{record_id}` 的约定是成功返回 HTTP 204，没有 JSON body；修改接口则继续返回完整记录，两者不能用完全相同的响应解析假设。
- 解决：请求层先判断 `response.status === 204` 并返回 `null`；删除流程把“服务端删除成功”和“明细重新读取失败”分开处理，避免重复删除或误报。
- 预防：为每个接口记录成功状态码和响应体约定，并在客户端用状态码分支；涉及押金关联的服务端业务错误继续显示冲突，不自动改成本地结果。

### 修改或删除服务端账目时网络中断

- 现象：页面内的账目使用服务端 UUID，直接把它写入旧的 localStorage 会让本地账户和押金关联失效。
- 解决：请求失败时先恢复本地完整快照，再用原账目的类型、类别、日期、金额、备注、账户名称和押金对象组成业务指纹定位本地记录；找到后才执行本地修改或删除。
- 预防：回退逻辑只接受稳定业务字段，不把跨数据源的 UUID 当成本地主键；若本地找不到唯一目标，就停止操作并明确提示用户。

### 账本或账户修改后刷新页面又出现旧数据

- 现象：服务端 `PATCH` 或 `DELETE` 已成功，但网络中断导致页面没有拿到后续总览或明细刷新，重新以本地模式打开时仍可能看到旧快照。
- 原因：渐进迁移阶段保留 localStorage 作为离线副本，服务端写入成功不会把服务端 UUID 强行写回旧本地主键；两份数据需要分别维护。
- 解决：成功写入后立即刷新服务端总览，账户删除再刷新当前账本明细；刷新失败只提示稍后重试，不把已经成功的服务端操作当成失败回滚。
- 预防：区分“写入成功”和“派生数据读回失败”两个状态；只有明确的网络写入失败才回退本地，业务冲突则保持原页面数据等待修正。

### 登录后业务接口仍然显示本地开发数据

- 现象：注册或登录成功后，`/api/auth/me` 返回真实用户，但没有带会话 Cookie 的旧请求仍能读取固定开发用户的账本。
- 原因：只有显式设置 `JIZHANGBEN_ALLOW_DEV_FALLBACK=1` 时才会启用固定开发用户回退；生产默认值为 `0`，没有 Cookie 的业务请求会返回 401。
- 解决：确认浏览器同源请求会自动携带 HttpOnly Cookie，并用 `/api/auth/me` 检查会话；保留默认值 `0`，网页登录后所有业务请求都必须有会话。
- 预防：不要把用户 ID 写入前端请求参数；所有业务资源都从服务端会话依赖取得当前用户，并为无 Cookie、无效 Cookie、跨用户 ID 分别保留测试。

### 页面显示已登录，但请求提示登录状态失效

- 现象：登录后停留较久，或服务端清理了会话，账本读取/保存返回 401。
- 原因：会话 Cookie 已超过有效期，或者服务端主动撤销了令牌；这不是普通网络断开，继续使用服务端 UUID 进行写入没有意义。
- 解决：请求层收到受保护接口的 401 后，会自动清除网页认证状态、恢复 localStorage 快照，并在顶部提示“登录状态已过期，请重新登录”。重新登录成功后再重新读取服务端账本。
- 预防：服务端查询会话时清理过期记录；部署时使用 HTTPS 和正确的 `JIZHANGBEN_CORS_ORIGINS`，并为过期会话保留前后端自动化测试。

### 登录成功后服务端账本暂时读不到

- 现象：顶部显示已登录，但账本、账户或明细暂时没有切换到服务端数据。
- 原因：登录认证和后续数据读取是多个请求；登录可能成功，但跨端口配置、服务端暂时不可用或某个响应格式错误。
- 解决：页面会保留登录身份，恢复本地快照，并在顶部提示服务端账本暂时无法读取；网络恢复后重新刷新或重新登录即可再次读取。
- 预防：不要把数据读取失败当成密码错误；分别测试登录成功、账本读取失败、会话 401 和主动退出四种状态。

### 迁移测试通过，但无法证明是真实登录用户

- 现象：迁移接口测试返回成功，但测试客户端没有保存注册后的 Cookie。
- 原因：每次请求都创建新的客户端时，旧测试可能显式打开固定开发用户回退，结果不能代表真实用户。
- 解决：使用同一个带 Cookie 的客户端完成注册、预览、导入、导出和总览读取；退出后再次查询，确认刚才用户的账本不再出现。
- 预防：涉及用户边界的接口测试必须显式复用会话，不能只依赖默认开发回退。

### 两个设备登录后看到的数据不一致

- 现象：手机端创建账目后，电脑端仍显示空账本或旧总览。
- 原因：两个客户端没有各自保存登录 Cookie，或者前端跨端口请求没有启用凭据传递，导致其中一端没有使用同一个服务端用户会话。
- 解决：确认前端请求使用 `credentials: "include"`，后端配置 `JIZHANGBEN_CORS_ORIGINS` 并允许凭据；退出后重新登录，再读取账本、账户、账目和总览。
- 预防：用两个独立 Cookie 容器做一端写入、另一端读取测试，再用第三个账号验证访问他人账本返回 404。
